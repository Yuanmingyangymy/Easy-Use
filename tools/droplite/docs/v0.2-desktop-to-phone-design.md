# DropLite v0.2 Desktop to Phone Transfer Design

This is the design document for the v0.2 desktop-to-phone feature. Phase 1 backend model and Phase 2 desktop send UI are implemented on the `feat/droplite-desktop-to-phone` branch; the mobile receive UI is still not implemented.

## Product Positioning

DropLite v0.2.0 Preview will build on the v0.1 phone-to-desktop flow by adding temporary desktop-to-phone transfer.

One-line positioning:

电脑丢进去，手机点一下就拿到。

English summary:

DropLite v0.2 adds a lightweight desktop-to-phone transfer flow so users can send text and files from the desktop app to a connected phone browser over the local network.

Target experience:

1. The user opens DropLite on the desktop.
2. The phone scans the QR code and joins the current temporary session.
3. The desktop shows a `Send to phone` area.
4. The desktop user enters text or drops files into DropLite.
5. The phone page shows receive cards from the desktop.
6. The phone user copies text or downloads files.
7. The flow still requires no account, uses no cloud service, and stores no transfer history.

## Required Scope

v0.2 should include:

- Keep the current session connection after the phone scans the QR code.
- Add a `Send to phone / 发送到手机` area on the desktop.
- Send text from the desktop to the phone.
- Select files on the desktop and make them available to the phone.
- Drag files into the desktop app and make them available to the phone.
- Show a pending receive list on the phone page.
- Let the phone copy received text.
- Let the phone download received files.
- Show file name, size, type, and send time on the phone.
- Keep sent content valid only for the current session.
- Reject outbox list and download access after token expiry.
- Invalidate old token access after `Refresh session`.
- Clear pending sent content when the app closes.
- Avoid cloud services.
- Avoid accounts.
- Avoid transfer history.

## Explicitly Out of Scope

v0.2 should not include:

- Multiple phones receiving at the same time.
- Device friend lists.
- Cloud relay.
- Public internet transfer.
- Background always-on sync.
- Chat.
- A mobile app.
- Automatic saving to the phone photo gallery.
- Folder sync.
- Complex device management.
- WebRTC.
- A database.
- Permanent history.
- Public sharing links.

Phone browser download behavior is controlled by the operating system and browser. iOS Safari, Android Chrome, and embedded browsers such as WeChat may behave differently. v0.2 should provide click-to-download and copy actions, but it should not promise automatic saving to the photo gallery.

## Technical Approach

Prefer continuing with the existing local HTTP service. Do not introduce WebRTC for v0.2.

The v0.2 branch also includes a separate product polish improvement: configurable phone-to-desktop receive folder. This is independent of the desktop-to-phone outbox. The receive folder controls where new files from the phone are saved; the outbox keeps backend-only references to source files chosen on the desktop.

Data flow:

```text
Desktop UI
-> Tauri/Rust backend
-> local outbox state
-> phone browser polling
-> phone displays received items
-> phone downloads item through token-protected endpoint
```

Implemented in Phase 1:

- `GET /api/outbox?token=<session-token>` lists current in-memory outbox items.
- `GET /api/outbox/:id/download?token=<session-token>` downloads registered file, image, or video items.
- `POST /api/outbox/:id/ack?token=<session-token>` marks an item as downloaded.
- Internal Rust methods add text and file outbox items for future UI integration.

Implemented in Phase 2:

- Tauri commands let the trusted desktop WebView add text and files to the outbox.
- The desktop UI includes a `Send to phone / 发送到手机` panel.
- The desktop UI can add text, choose files with the native dialog, and accept dropped files from Tauri file drop events.
- The desktop UI lists outbox items without displaying local absolute paths.

Still planned for later phases:

- Phone-side polling UI and copy/download cards.

Suggested API shape:

- `GET /api/outbox?token=<session-token>` lists items waiting for the phone.
- `GET /api/outbox/:id/download?token=<session-token>` downloads a file item.
- `POST /api/outbox/:id/ack?token=<session-token>` marks an item as claimed or downloaded.
- `add_outbox_text(content)` adds a text item through a Tauri command or internal Rust API.
- `add_outbox_file(path)` adds a file item through a Tauri command or internal Rust API.
- `GET /api/session?token=<session-token>` continues to expose phone-side session state.

Polling is preferred first because it is simple, stable, compatible with mobile browsers, easy to debug, and unlikely to destabilize the v0.1 upload path. A future version can move to WebSocket if the product need becomes clear.

Recommended polling interval: 1 to 1.5 seconds. Avoid overly frequent requests.

## State Model

Phase 1 implements this server-side shape in Rust:

```ts
type OutboxItem = {
  id: string;
  kind: "text" | "file" | "image" | "video";
  displayName: string;
  mimeType?: string;
  sizeBytes?: number;
  createdAt: string;
  status: "pending" | "downloaded" | "expired";
  content?: string;
};
```

Text items include full text content so the phone can copy it directly. File items store a safe backend-only file reference. The phone never receives local absolute paths. Download URLs are generated through the API.

State rules:

- Outbox items exist only in memory.
- The app clears them when it closes.
- Items expire with the current session.
- Refreshing the session clears the outbox.
- No database is needed.
- No permanent history is stored.
- Local absolute paths are not exposed to the phone.
- The download endpoint can only access files registered in the current outbox.

## Security Design

v0.2 still follows DropLite's Local-first / No account / No cloud principles.

Security requirements:

- Every outbox API must validate the session token.
- Expired tokens must be rejected for outbox lists and downloads.
- Download routes must not read arbitrary paths from request parameters.
- Files must come from an explicit desktop user action: choose file or drag file.
- The backend should keep safe references and not expose absolute filesystem paths to the phone.
- Filenames used in `Content-Disposition` must be sanitized.
- Text content should remain only in the current session.
- Closing the app clears the outbox.
- `Refresh session` clears the current outbox to avoid making old pending items available under a new pairing context.
- The transport is still local-network HTTP and is not suitable for public or untrusted Wi-Fi.
- No cloud service, tracking, or account system should be introduced.

## UI Design

### Desktop

The v0.1 desktop UI already includes:

- QR code.
- Recently received list.
- Safety hints.
- Session timer.
- Refresh session.
- Language selector.

v0.2 can add a focused `Send to phone / 发送到手机` area with:

- Text input.
- `Send text` button.
- File picker button.
- Drag-and-drop file area.
- Pending and sent item list.
- Small status messages for send, downloaded, expired, and errors.

Keep the interface simple. Two clear regions may work well:

- `Receive from phone`.
- `Send to phone`.

### Phone

The scanned phone page can use two sections:

- `Send to desktop`: keep the v0.1 text/photo/video/file send controls.
- `Receive from desktop`: show desktop-sent text and file cards.

Phone cards:

- Text card: show a readable preview and `Copy text`.
- File card: show name, size, MIME type or kind, sent time, and `Download`.

Mobile layout must remain compact and touch friendly.

## v0.1 Regression Risk

v0.2 must not break the v0.1 verified flow:

- Phone sends text to desktop.
- Phone sends images to desktop.
- Phone takes a photo and sends it to desktop.
- Phone sends videos to desktop.
- Phone sends generic files to desktop.
- Timestamp-based file naming.
- Recently received list.
- Token expiry.
- Refresh session.
- Windows Private network hint.
- English and Simplified Chinese UI.

Regression checklist:

1. Start DropLite.
2. Scan QR code with a phone.
3. Send text from phone to desktop.
4. Send photo from phone to desktop.
5. Take photo and send.
6. Send MP4 from phone to desktop.
7. Send PDF or ZIP from phone to desktop.
8. Confirm files use timestamp names and no `.part` files remain.
9. Confirm Recently received updates.
10. Confirm expired token rejection.
11. Refresh session and verify old token fails.
12. Switch English and Simplified Chinese.
